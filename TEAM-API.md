# naruprof-eclipseDitto: team integration guide

The **Ditto module** (the "twin") keeps a private, rebuildable copy of one learner's progress summary
in Eclipse Ditto. It **reads** from NARU over gRPC and **serves** one summary endpoint to Vert.x.
Kong never talks to it directly.

```
                       Tailscale network (tailnet)
 ┌──────────────┐  gRPC :9092 (LearningProjection)   ┌──────────────────────────┐
 │ NARU         │ ◀───────────────────────────────── │ TWIN (this module)       │
 │ teammate     │  authorization: Bearer             │ 100.108.239.95:8083      │
 └──────────────┘  TWIN_TO_NARU_TOKEN                │  └─ Ditto (private)      │
                                                     └──────────────────────────┘
 ┌──────────────┐  GET /internal/v1/profiles/{id}/summary        ▲
 │ Vert.x       │ ───────────────────────────────────────────────┘
 │ teammate     │  Authorization: Bearer VERTX_TO_TWIN_TOKEN
 └──────────────┘
        ▲  /api/naruprof/twin/summary
 ┌──────────────┐
 │ Kong         │  routes /api/** to Vert.x as usual; never routes to the twin or Ditto
 └──────────────┘
```

Contract: `implementation-prompts/contracts/integration-v1.md` and `learning_projection_v1.proto` (unchanged).

## 3. Steps for the NARU teammate

The twin is a **client** of NARU's published gRPC service `naruprof.learning.v1.LearningProjection`.

### Environment variables to set on NARU

| Variable | Value | Source |
|---|---|---|
| `NARUPROF_PROFILE_ID` | `f7933216-20db-49cb-90e0-3a9d5396966d` (or a UUID you provision; then tell Ghayeth) | section 1 |
| `TWIN_TO_NARU_TOKEN` | `3d20fa89b76a4aef9c906641e273e7ecac39534b0e2f72a9` | section 1 (generated by Ghayeth; do not generate your own) |
| gRPC listen address | `0.0.0.0:9092`, or `<your-tailscale-ip>:9092` | must be reachable from `100.108.239.95` |

### What to implement / check

1. **Expose** `LearningProjection` from `learning_projection_v1.proto` (package `naruprof.learning.v1`,
   unchanged) on port `9092`, reachable over Tailscale. Plain gRPC (no TLS); Tailscale encrypts.
2. **Authenticate** every call: metadata key `authorization` (lowercase) must equal
   `Bearer <TWIN_TO_NARU_TOKEN>`. Missing → `UNAUTHENTICATED`; wrong → `PERMISSION_DENIED`.
3. **Profile fence:** only `NARUPROF_PROFILE_ID` is served. Unknown profile → `NOT_FOUND`.
4. **`GetSnapshot(Profile)`** returns the current full state: `profile_id`, `sequence`, and exactly one of
   `summary` or `deleted`. An existing empty profile is `sequence 0` with four zero counts.
5. **`Watch(WatchRequest{profile_id, after_sequence})`** replays every revision **greater than**
   `after_sequence` in order, then streams new ones. Rules:
   * `sequence` increases by exactly 1 per committed change, **never goes backwards**, survives restarts;
   * commits made between the twin's `GetSnapshot` and its `Watch` must be replayed (no gap);
   * cursor expired or ahead of head → `OUT_OF_RANGE` (the twin then takes a new snapshot);
   * honour gRPC flow control (the twin requests messages one at a time);
   * redelivery after reconnect is fine; the twin ignores duplicates.
6. **Counts** in `summary` (uint64): `teaching_sessions` (chats with missing kind count as teaching),
   `practice_sessions`, `propositions` and `reasoning_chains` (distinct stored records after canonical merge;
   canvas junctions are not chains).
7. **Deletion:** a deleted profile keeps a retained tombstone (`deleted {}`) at the next sequence.

### Self-test with grpcurl (before telling the Ditto owner)

From any tailnet machine, in the folder holding `learning_projection_v1.proto`:
```bash
grpcurl -plaintext -import-path . -proto learning_projection_v1.proto \
  -H "authorization: Bearer <TWIN_TO_NARU_TOKEN>" \
  -d '{"profile_id":"<uuid>"}' <your-ip>:9092 naruprof.learning.v1.LearningProjection/GetSnapshot

grpcurl -plaintext -import-path . -proto learning_projection_v1.proto \
  -H "authorization: Bearer <TWIN_TO_NARU_TOKEN>" \
  -d '{"profile_id":"<uuid>","after_sequence":0}' <your-ip>:9092 naruprof.learning.v1.LearningProjection/Watch
```
Expected: a snapshot JSON, then a stream of revisions `1..n`. Without the header → `Unauthenticated`.

**Reference implementation** of the expected server behaviour (the fake NARU the twin is tested against):
`twin-fixture-naru/src/main/java/org/naruprof/twin/fixture/naru/FakeLearningProjection.java`.

**Then:** send your Tailscale IP and port to the Ditto owner (section 2, step 6).

## 4. Steps for the Vert.x teammate

Vert.x exposes the twin's summary to the app as **`GET /api/naruprof/twin/summary`**.

### Environment variables to set on Vert.x

| Variable | Value | Source |
|---|---|---|
| `TWIN_URL` | `http://100.108.239.95:8083` | Ditto owner |
| `VERTX_TO_TWIN_TOKEN` | `8f5452b2ddfb6b92463d0d93cb33dd7419f1b42d2087304b` | section 1 (generated by Ghayeth; do not generate your own) |
| `NARUPROF_PROFILE_ID` | `f7933216-20db-49cb-90e0-3a9d5396966d` | section 1 |

### What to implement

1. Route **`GET /api/naruprof/twin/summary`** (read-only; no other methods).
2. Call **`GET {TWIN_URL}/internal/v1/profiles/{NARUPROF_PROFILE_ID}/summary`** with header
   `Authorization: Bearer {VERTX_TO_TWIN_TOKEN}`.
   * The profile id comes from **configuration only**, never from the browser's query, path or headers.
   * Never forward the browser's own `Authorization` header to the twin.
3. **Relay status code and body unchanged** (200 / 404 / 503, see section 7). Keep `Content-Type: application/json`.
4. If the twin is unreachable or times out (suggested timeout: 5 s), answer
   `503 {"code":"twin_unavailable"}`. Ordinary learning routes must keep working when the twin is down.
5. Keep the token server-side only (not in SSE, page data or logs).

Sketch with Vert.x `WebClient`:
```java
router.get("/api/naruprof/twin/summary").handler(ctx ->
  webClient.getAbs(twinUrl + "/internal/v1/profiles/" + profileId + "/summary")
      .putHeader("Authorization", "Bearer " + vertxToTwinToken)
      .timeout(5000)
      .send()
      .onSuccess(r -> ctx.response().setStatusCode(r.statusCode())
          .putHeader("Content-Type", "application/json").end(r.bodyAsBuffer()))
      .onFailure(e -> ctx.response().setStatusCode(503)
          .putHeader("Content-Type", "application/json").end("{\"code\":\"twin_unavailable\"}")));
```

### Self-test

```bash
# 1. direct call to the twin (from your machine, over Tailscale)
curl -H "Authorization: Bearer <VERTX_TO_TWIN_TOKEN>" \
  http://100.108.239.95:8083/internal/v1/profiles/<uuid>/summary
# 2. through your Vert.x route: must return exactly the same status and body
curl http://localhost:8081/api/naruprof/twin/summary
```

## 7. API reference

Base URL on the tailnet: **`http://100.108.239.95:8083`**. Ditto (`:8090`) is **not** reachable from the tailnet, by design.

### 7.1 Summary (Vert.x)

```
GET /internal/v1/profiles/{profileId}/summary
Authorization: Bearer <VERTX_TO_TWIN_TOKEN>
```

| Status | Body | Meaning |
|---|---|---|
| **200** | six fields below | revision actually applied in Ditto (may lag NARU by a moment) |
| **404** | `{"code":"twin_missing"}` | profile deleted (confirmed tombstone) |
| **503** | `{"code":"twin_unavailable"}` | twin bootstrapping, or Ditto unreachable |
| **401** | `{"code":"unauthorized"}` | missing or wrong token |
| **403** | `{"code":"forbidden"}` | another profile id, or a token of another role |
| **400** | `{"code":"invalid_profile_id"}` | not a UUID |

All responses: `Content-Type: application/json`, `Cache-Control: no-store`.

```json
{"profileId":"f7933216-20db-49cb-90e0-3a9d5396966d","sequence":"3","teachingSessions":"1","practiceSessions":"1","propositions":"2","reasoningChains":"1"}
```

| Field | Meaning |
|---|---|
| `profileId` | pseudonymous learner profile (lowercase UUID) |
| `sequence` | NARU revision this summary reflects; compare with NARU to judge freshness |
| `teachingSessions` | teaching chats (missing `kind` counts as teaching) |
| `practiceSessions` | practice chats |
| `propositions` | distinct stored propositions |
| `reasoningChains` | stored argument chains |

All values are **strings** holding unsigned 64-bit integers: parse with `Long.parseUnsignedLong` (Java)
or `BigInt` (JS), never as floats. The twin never invents zeros: no confirmed data means 503.

### 7.2 Health (Kong, monitoring; no token)

| Endpoint | 200 when | 503 when |
|---|---|---|
| `GET /internal/health/live` | process running | (not used) |
| `GET /internal/health/ready` | Ditto read works and projection initialized (data or confirmed deletion) | bootstrapping, Ditto down |

### 7.3 Operator only (Ditto owner, `TWIN_MAINTENANCE_TOKEN`)

| Endpoint | Purpose |
|---|---|
| `GET /internal/v1/projection/status` | checkpoint, applied vs. NARU revision, lag, consumer state, last failure, circuit breaker |
| `POST /internal/v1/maintenance/profiles/{id}/reconcile` | force a resync from NARU's snapshot |
| `POST …/reconcile?acceptSourceRestore=true` | accept a NARU restored to an older revision (`RESTORE_CONFLICT`) |

## 8. Troubleshooting

| Symptom | Who | Likely cause / fix |
|---|---|---|
| Connection refused / timeout to `:8083` | Vert.x, Kong | twin not running, `TWIN_PUBLISH_ADDRESS` not set to the Tailscale IP, Tailscale off, or firewall (section 2, step 7) |
| 401 from the twin | Vert.x | wrong or missing `VERTX_TO_TWIN_TOKEN`, or `Bearer ` prefix missing |
| 403 from the twin | Vert.x | `NARUPROF_PROFILE_ID` differs from the twin's |
| 503 that never clears | Vert.x | twin can't reach NARU or Ditto; owner checks `docker compose logs twin` |
| Twin log: `NARU rejected the twin's credential` | NARU, owner | `TWIN_TO_NARU_TOKEN` differs on the two sides, or metadata key not lowercase `authorization` |
| Twin log: `NARU does not know profile` | NARU | profile id not provisioned on NARU, or different UUID |
| Twin log: `source failure state=SOURCE_UNAVAILABLE` | NARU | NARU not reachable at `NARU_GRPC_TARGET` (IP, port, bind address, firewall) |
| Status shows `RESTORE_CONFLICT` | owner | NARU's `sequence` went backwards (NARU restarted with lost history or restored). Fix NARU, then `reconcile?acceptSourceRestore=true` or `down -v` |
| `sequence` lags NARU | anyone | normal for under a second; if it persists, check `/internal/v1/projection/status` (`consumerState`, `lastFailureClass`) |
